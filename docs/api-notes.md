# BambooHR API behaviour observed while building these modules

Everything below was **observed** with read-only requests against one production account between 2 and 7 October 2026, using an
API key (HTTP Basic). It is not BambooHR documentation and may not hold for every account or for later API versions. Each item
is exercised by a test against an invented fixture (`t/data/README.md`). Items marked *unverified* are inferences or gaps.

## Metadata

* **`GET /v1/meta/fields`**: an array of `{id, name, type[, alias][, deprecated]}`.
  * `id` is a JSON number for ordinary fields and a JSON **string** for sub-fields such as `"1234.6"`. Normalise to strings.
  * **Display names are not unique** within an account (two fields can both be `Hire Date`), and **some aliases are shared**.
  * Display names can carry stray whitespace (a trailing space, doubled interior spaces). Two names can differ only in whitespace.
  * **One id can be listed more than once**, with a different name and alias each time (seen where a field was renamed). A reader that keys by id
    silently loses all but one of them.
  * A custom table's columns are also listed here, but **usually without their alias**.
* **`GET /v1/meta/tables`**: an array of `{alias, fields: [{id, name, alias, type}]}`.
  * There is **no display name for a table**: identify tables by alias.
  * Column aliases here can differ from, or exist only here and not in, `/meta/fields`. Treat this endpoint as the source of
    truth for column aliases.
* **`GET /v1/meta/lists`**: an array of list definitions with the keys `fieldId, id, manageable, multiple, name, options`
  (some entries also have `alias`). Each option has `id, name, archived, archivedDate, createdDate, manageable`.
  Match a list to a field by `fieldId`. *Unverified:* the values `archived` can take (the code assumes `yes`/`true`/`1`).
* `GET /v1/hris/custom-fields` is not used: BambooHR's reference lists OAuth2 only for it.

## Aliases

* Generated by BambooHR: `custom` + the display name with spaces removed, **punctuation kept** (`#`, `?`, `,`, `(`, `)`, `/`, `*`, `'` all
  occur), and a numeric suffix on collision (`customEffectiveDate2`, `3`, `4`). They cannot be predicted: read them back.
* A table whose alias contains an **apostrophe** returned an HTML 404 on every endpoint, raw or percent-encoded. A table with a hyphen worked.
  Avoid punctuation when naming tables and columns.
* Because aliases can contain characters that break a query string, request fields by **numeric id**.

## Reading data

* **Table rows** (`GET employees/{id}/tables/{table}`, `GET employees/all/tables/{table}`): an array of flat objects keyed by the **column alias**, plus
  `id` and `employeeId`. Both are JSON numbers for custom tables and JSON strings for standard tables. An empty value is `null` or `""`.
  An employee with no rows gets `[]`.
* **`employees/all/tables/{table}`** returns every employee's rows in one response. No pagination was visible at a few hundred KB.
* **`GET employees/changed/tables/{table}?since=`**: `{employees: {ID: {lastChanged, rows: [...]}}, table}`. Rows carry no `id` or `employeeId`.
* **`GET employees/changed?since=`**: `{employees: {ID: {id, action, lastChanged}}, latest}`. *Observed:* it is bursty. A bulk job once stamped about
  half of all employees with one timestamp, and on ordinary days it listed every employee anyone had edited. It cannot tell you whether a
  *specific table* changed.
* **The same field comes back under different keys** depending on the call: `GET employees/ID?fields=<id>` keys it by id, `?fields=<alias>` by alias,
  and `POST reports/custom` by an alias that `/meta/fields` may not list. `WebService::BambooHR::MappingValidator::employee_value` tries each.
* Every table endpoint honoured `Accept: application/json`; `Accept: application/xml` returned XML.
* Both `https://api.bamboohr.com/api/gateway.php/{company}/v1` and `https://{company}.bamboohr.com/api/v1` worked with an API key.
* No `Retry-After` or rate-limit headers were seen on 40-odd sequential requests. Behaviour under load is *unknown*.

## Not verified

* Writes (`add_row`, `update_row`, `delete_row`) were never run against a real account.
* Whether terminated employees appear in `employees/all/tables/{table}` and `reports/custom`.
* The shape of an `options` element beyond its keys, and rate limits.
